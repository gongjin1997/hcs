## 优先处理：已复现的采集隔离问题

### P1-1 Event 接口失败阻断 Pod 状态采集

- 位置：`backend/app/k8s/collector.py:187`。先取得 Pod 清单，再调用 `kube.events()`；后一调用抛错后，尚未进行 Pod 状态入库、重启/OOM/CrashLoop 检查。
- 复现：合成 Pod 明确处于 CrashLoopBackOff；Pod 查询成功、Event 查询返回 503。结果为 PodState 0 行、工作负载观测 0 条。
- 影响：Event 权限不足或短时不可用，可能同时丢失本来可以从 PodStatus 获取的实时异常证据。Kubernetes 官方将 Events 定义为尽力而为、保留时间有限的补充信息，不宜让它成为 PodStatus 采集的硬性前置条件。
- 建议：分别记录 Pod/Event 两条查询结果；Pod 清单完整时继续处理其状态，Event 源标记不可用。真实 API 错误仍计入任务失败诊断，Event 相关未知值不能补零或触发恢复；Pod 清单不完整时仍不得标记 Pod 删除。
- 验收：Event 503/403 时 Pod CrashLoop/OOM/重启证据仍能处理；已有 Event 告警不因源缺失误恢复；Pod 分页失败仍不产生删除判定。

### P1-2 单个无效事件影响同集群全部工作负载

- 位置：`backend/app/k8s/collector.py:127,352,545`。未知状态按 `cluster_id + event_type` 保存，计数时同集群同类型全部返回未知。
- 复现：工作负载 B 的合法驱逐事件为 2 次，单独采集可输出 `evicted_1h=2`；加入工作负载 A 的无效 count=0 事件后，B 的事件仍以 2 次入库，但 B 的 `pod_evicted` 观测消失。任务均为 SUCCESS，说明不是新一轮平台误告警，而是判定范围过宽。
- 建议：按租户、项目、集群、namespace、Pod UID/已确认工作负载和事件类型隔离精度缺口。能确认所属对象时只影响该对象；不能确认归属时明确扩大范围，不能按名称猜所属 Deployment。
- 验收：A 的无效事件不屏蔽 B 的真实事件；跨租户/项目/namespace 仍隔离；A 的未知值不补零、不误恢复；日志仅保留聚合 INFO。

### P1-3 Pod 汇总未区分当前状态和过期快照

- 位置：`backend/app/api/v1/pod_events.py:195,218`、`frontend/src/views/pods/PodEventsView.vue:17`。统计所有未标记 deleted 的 PodState，未按 `last_seen` 区分新鲜度；页面就绪卡片直接显示 ready/total。Pod 详情虽有 `last_seen`，不等于汇总已体现新鲜度。
- 复现：写入一份 72 小时前的 Ready Pod 快照，再以当前时间查询 24 小时统计。结果仍返回 total=1、ready=1，汇总没有 freshness/last_collected_at 等字段。
- 建议：按租户/项目/集群输出最近成功采集时间、快照年龄和可用状态；过期快照保留供查阅，但当前就绪汇总单独标记过期/未知，不把旧 Ready 状态当作新鲜正常。阈值复用任务周期及现有新鲜度规则，不另加周期性精度告警。
- 验收：停止采集后汇总明确过期；成功恢复采集后转为新鲜；不同项目不能共用最近采集时间；历史事件和已有告警不被删除或误恢复。

### P1-4 管理面节点健康信息已取得，但只保留节点数量

- 位置：`backend/app/ledger/fetchers.py:271–281`。节点清单只用于 `len(nodes)`；`status.phase`、`lastProbeTime`、`serverId`、`privateIP` 未保存，尚无独立节点资源/健康采集链路。
- PDF §4.3.3 表 4-371 NodeStatus，印刷 **478 / 物理 484**，明确给出 Build、Installing、Upgrading、Active、Abnormal、Deleting、Error，并说明 `lastProbeTime` **超过 5 分钟的节点状态不具有参考意义**。该页已渲染核对表格与页脚。
- 建议：保留节点 UID、状态、上游检查时间、底层 ECS/BMS ID 和私网地址，按原始检查时间标记有效/过期；不能用本地请求时间覆盖上游检查时间。先提供只读健康视图，新增状态告警另行校验并沿用用户配置。
- 当前台账默认周期为 3600 秒，而容器事件为 60 秒（`backend/app/services/bootstrap.py:27–28`）；节点健康不能直接把小时级台账当作实时采样，应与静态台账分开设置周期并受现有开关/QPS 控制。新增能力不得自动打开原本关闭的租户采集或通知。
- 验收：Active/Abnormal/Error 分别搭配 4分59秒、5分01秒和无效/缺失检查时间；过期/未知状态不作为健康或恢复依据；按 `serverId` 关联 ECS 时仍校验租户与项目范围。

## 后续能力：需要核对集群内原生 API 能力

### P2-5 用 ownerReferences 完整关联工作负载

当前 `backend/app/k8s/semantics.py:8` 保留 Pod 的直接 controlling owner，因此 Deployment 的 Pod 通常归到 ReplicaSet，Job 的 Pod 归到 Job。这比根据名字后缀推断安全，但滚动更新时同一业务可能分成多个 ReplicaSet 条目。

可在确认只读 RBAC 后，读取 ReplicaSet/Job 的 ownerReferences，按 UID 验证链路，补充 Deployment/CronJob 顶层关系；直接 owner 和顶层 owner 都保留。不要回退到“截名字后缀就是 Deployment”的逻辑，也不应因为缺少额外权限阻断现有 Pod 采集。

### P2-6 按能力接入 CPU/内存，不依赖 AOM

CCE 管理面节点规格、容量和状态不等于 CPU/内存实时使用率。可在单独验证集群支持的 API 组、版本与只读权限后，使用 Kubernetes Resource Metrics API 获取当前样本；它也不自动提供历史趋势、磁盘利用率或完整应用指标。缺少能力时显示未启用/不支持，不能补零或周期性产生配置类告警。自定义背压探针维持现有显式配置。

PDF 印刷 1266–1267 / 物理 1272–1273 的监控说明提到 Prometheus 插件，但不足以证明正式环境已部署指标组件、开放了哪个查询版本或具备对应 RBAC；不直接增加未经核实的采集请求，不回退 AOM。
