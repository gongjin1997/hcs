# 全系统复核：平台任务运行监控与项目维度（2026-11-02，第二轮）

## 1. 范围与已明确的契约

运行身份是 **task_code × tenant_id × project_ref**，不是单 task 或 task × tenant。

| 情况 | 失败链 / 告警 | 展示与成功时间 |
| --- | --- | --- |
| 已知同项目 SUCCESS 且 finished_at 存在 | 重置未成功链；只有同任务、同租户、同项目才能恢复任务失败及 401/403 告警 | 成功时间取真实 SUCCESS 的 finished_at；不能用 PARTIAL 或最近任意记录代替 |
| FAILED / TIMEOUT / PARTIAL | 都是一次已执行但未成功，连续未成功数 +1；达到配置阈值触发平台告警 | 原始状态保留，不包装 SUCCESS |
| SKIPPED / RUNNING | 不增加失败数，也不清零；不恢复活动告警 | 最新原始状态保留；effective_status 指向上一次真实执行，失败证据仍展示 |
| project_ref=NULL 且不是全局清理 | 历史未知项目，独立保留；不得映射到租户唯一 / 第一个项目，也不能根据已知项目或未知项目 SUCCESS 自动恢复 | 标为 UNKNOWN / 历史未知项目；未知桶内成功不能证明先前失败已恢复；历史真实 SUCCESS 时间只属于这个未知桶 |
| data_cleanup 且 tenant_id=NULL / project_ref=NULL | 明确的全局内部任务，不是缺项目的 HCS 任务；同全局任务 SUCCESS 可以恢复 | 标为 GLOBAL / 全局内部任务 |
| 尚无运行 / 停用 | 尚无运行显示 UNKNOWN；停用显示 DISABLED，不伪装健康 | 不制造成功率 0 / 最近成功时间 0 |

运行先后按 `coalesce(finished_at, started_at), id` 确定；延迟旧回调不得覆盖较新的执行结果。401/403 可能是特定服务权限问题，所以同项目另一任务成功也不足以证明原失败接口恢复。

**手工执行共用结论**：`platform_watch.run_outcome(runs, skipped=False)`。

- 全部 SUCCESS 且无外部跳过：SUCCESS。
- 全部 FAILED / TIMEOUT：FAILED（端点返回 502，保留每个项目原始 TIMEOUT / FAILED）。
- 有 PARTIAL、成功与失败混合、成功与跳过混合：PARTIAL。
- 无运行 / 全 SKIPPED：SKIPPED。
- 存在运行中的任务：RUNNING，不能冒充成功。
- 审计仅完整 SUCCESS 记为 SUCCESS；其他结果在 detail.outcome 保留精确结论，不以 HTTP 200 等同任务成功。

## 3. 已证实并修复的问题

| 问题 | 原实现与后果 | 落地修复 |
| --- | --- | --- |
| 项目身份缺失 | InspectionRun 仅 tenant_id，同租户项目运行串用 | 新增 nullable project_ref 及复合索引；新生产者写真实 target.project_ref，旧行不回填 |
| PARTIAL 假恢复 | on_run 将 SUCCESS/PARTIAL 一起 resolve | 只有已知同项目、同任务、真实完成的 SUCCESS 才能恢复；历史未知不自动恢复 |
| TIMEOUT 漏计 / SKIPPED 截断失败链 | 只认 FAILED，任意其他状态都截断连败 | FAILED/TIMEOUT/PARTIAL 计入未成功；SKIPPED/RUNNING 中性，保留前序失败 |
| 跨项目成功掩盖失败 | 任务 key 只有 task+tenant，认证 key 只有 tenant | 新 key 包含项目，认证 key 另含任务；旧未知 key 保留为未知，不自动收编 |
| 延迟回调倒写 | 较旧 SUCCESS 回调可能恢复较新失败 | 按完成时刻和 id 验证当前有效执行，过期回调不改告警 |
| dashboard 只取最新单条 | 快项目最新 SUCCESS 掩盖其他项目故障 | 先按完整 scope 聚合，再取最差状态；额外返回 scopes，每个项目可核对 |
| CLI 只看 40 条、platform 只看 60 条 | 高频租户占满窗口，低频失败项目完全消失 | SQL 窗口聚合所有保留历史，不用全局条数上限；只加载每 scope 最新 ORM 行 |
| task API 全局只取 12 条 | 各项目最近运行展示不全 | 每个 task/tenant/project 独立保留最近 12 条；已知项目 / unknown_project 可分别筛选，不能同时选择 |
| metrics 缺项目标签 / 26h 截断 | 不同项目覆盖，老成功时间消失；孤立租户名 '-' 也可能混组 | 键使用原始 tenant_id/project_ref；增加 tenant_id/project_ref/project_scope 标签；成功时间跨保留历史检索，缺失不补 0 |
| 手工执行结论假成功 | system / pod collect 仅 FAILED 进入失败集合，PARTIAL/TIMEOUT/SKIPPED 被报 SUCCESS | 两端共用 run_outcome，TIMEOUT 参与全失败判定；返回 project_ref；审计保留精确 outcome |
| dashboard Pod 次数错误 | 重启 / OOM 按数据库事件条数计数，忽略 count、窗口、未重启 OOM；同名工作负载合并 | 共用 window_count；restart_counted=false 不算重启；窗口未知为 None；按 tenant/project/cluster/namespace/workload_kind/workload 分组 |
| UI 项目折叠及跳过算成功率分母 | latestByTenant 合并同租户所有项目；仅跳过也展示成功率 0 | 独立显示各项目与历史未知，SKIPPED 中文标记；成功率只对已执行记录统计，未知显示未知 |
| CLI WARN 仍打印“结论正常” | 未成功 / 无记录任务虽然标记 WARN/UNKNOWN，最后仍像完全健康 | 结论明确“需关注 / 未达到连续失败阈值”，不伪造正常；既有故障阈值退出码契约保留 |

## 5. 接口与前端交接

1. TaskRun / TaskRunResult.runs：增加 `project_ref`；任务历史另有 `project_scope`（PROJECT/UNKNOWN/GLOBAL）、`project_label`。
2. `/system/tasks`：新增 `scopes`、`history_limit_per_scope=12`；`project_ref`（正整数）与 `unknown_project` 查询条件互斥。每 scope 历史按完成时刻/id 排序，不再让全局 12 条漏项目。
3. `/system/platform` 的 `tasks[].tenants` 为兼容名称，实际每条是独立 tenant/project scope；增加 `project_ref/project_scope/project_label/effective_status/effective_run_id`。tasks.status 可为 UNKNOWN / DISABLED，不能按原 OK/WARN/FAILED 三值强行解释。
4. dashboard `tasks[].scopes` 含上述身份与状态；根 last_status 是最差 scope 状态，不再等于最新单条 SUCCESS。历史未知 / 缺完成时间的成功不能包装为已知范围整体 SUCCESS。
   执行状态与项目身份分开：有历史 SUCCESS 记录且没有未解失败，不因 project=NULL 改成“未运行”。增加 `scope_verified=false` 明示身份未知；缺完成证据 / 未解未知桶失败以 PARTIAL 表达。`last_status` 仅 SUCCESS/PARTIAL/FAILED/TIMEOUT/RUNNING/SKIPPED 或无记录时 null，均与 TASK_STATUS 对齐。
   `representative_scope(run_id,tenant_id,project_ref,project_scope)` 对应最差当前执行状态的时间 / 耗时；**不用于冒充跨项目对象总数**。当前检查对象与异常数改为 nullable：按 task/tenant/project 每范围取最近实际执行（SKIPPED/RUNNING 不代替实际执行），只有完整覆盖当前启用租户及项目、且每范围最近实际执行均为完整 SUCCESS，才汇总；否则 null，不补 0、不回退更旧成功。
   `count_basis=LATEST_COMPLETE_KNOWN_PROJECTS` 表示已验证的项目汇总；`GLOBAL_RUN` 为全局清理；`UNVERIFIED_PROJECT_COVERAGE` 为数量未知。`counts_complete`、`expected_scope_count`、`counted_scopes(tenant_id,project_ref,run_id,finished_at)` 可核查来源。`history_unknown_scope_count` 单独标明旧未知桶；其数量 **完全不参与当前总数**，且已知项目记录存在时历史未知不覆盖当前执行状态。专项明确验证 ECS **34+15=49，不能加 legacy 49 成 98**；台账 **100+96=196，不能加 legacy 196 成 392**。
   这些数量是最近完整执行检查对象数，不宣称实时台账去重资源总数；每个来源的实际完成时刻随 counted_scopes 返回。
5. dashboard `pods.restarts_24h/oom_24h`、`top_restart[].count` 可为 null；Top 行增加 `tenant_id/project_ref/cluster_id/namespace/workload_kind/workload_name/scope_key`。ongoing 项增加项目与 kind；前端列表 key 应使用 scope_key，不按同名 workload 合并。
6. `/metrics` 任务指标增加 `tenant_id/project_ref/project_scope` 标签：NULL project_ref 显式为 `unknown`。已有抓取规则需保留项目标签，不能先聚合掉项目再判“恢复”。last_success 为 SUCCESS.finished_at；无有效成功样本时不发该序列，不补 0。
7. 手工 system / pod / resources 的消费者应处理 SUCCESS/PARTIAL/FAILED/SKIPPED/RUNNING，不能把 HTTP 200 或无 FAILED 元素视为完整成功。

已把这些新增 / nullable 契约告知主代理：`TaskBrief.resource_total/abnormal_total` 可空，另需 counts_complete、count_basis、counted_scopes、expected_scope_count、history_unknown_scope_count、scope_verified。共享 `types/index.ts`、dashboard 视图、公共接口清单仍由主代理整合，不在此擅改。

其中 api/index.ts 的容器查询参数转发缺口按追加授权局部落地，其余共享返回类型仍交主代理；没有修改共享 types/index.ts。

### 报表 → 容器事件精确范围追加整合

- URL 支持 `tenant_id`、`project_ref`、`workload_kind`，历史未知项目必须显式 `unknown_project=1`。非法数字、冲突已知/未知条件不静默退回全范围；报表租户与顶栏冲突时阻止混合查询。
- `loadEvents`、`loadStats`（含进行中背压子查询）、`loadPods`（PodState 筛选元数据）都转发精确租户/项目；stats 中 PodState 计数也应用相同 workload / workload_kind，不只过滤事件。

- 工作负载选项按 tenant/project/cluster/namespace/kind/name 区分；Top 行点击带完整身份，缺少精确身份不会回退查询其他项目。
- 后端 list/stats/options 增加 unknown_project，list/stats 增加 workload_kind；Top workload 增加 workload_kind。tenant_id 查询参数始终和已授权 Scope 取交集，不能扩大权限。
- 新专项 `backend/tests/test_pod_report_scope_review_20261102.py`、`frontend/tests/podReportScopeReview20261102.test.ts`。后者修复前 5 failed，修复后通过；HTTP 用例验证同名 Job/StatefulSet、跨项目、未知项目和越权查询不混合。
