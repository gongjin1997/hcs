# 代码更新与默认开关验收

日期：2026-10-28。本轮验证使用 ARM64 镜像、QEMU 和独立临时数据库；没有连接或改动原生产数据库、真实 HCS、原部署密钥及现有局域网服务。

## 默认开关

- 新生产环境初始化：18 项全局采集开关、10 项巡检任务全部关闭，包括台账同步与数据清理；首次启动没有租户、资源或巡检运行记录。
- 新租户仍按原约定逐类型关闭采集。旧环境不补写关闭型全局覆盖；已有开关、任务启用状态、周期和参数均保留。
- 旧库缺失采集行时的兼容语义仍为开启，避免升级把旧环境整体关掉；新生产库通过显式关闭记录实现安全默认。

## 仅代码更新

- 首次安装携带四个 ARM64 运行时镜像及独立代码包。后续代码包只有后端源码/迁移、已构建前端、依赖清单及可选 wheels，不含镜像。
- `bash deploy.sh update 代码包.tar.gz` 在校验与依赖检查后备份内置数据库、执行迁移、切换版本目录并重新创建应用容器。
- 实测新增后端模块与前端静态文件生效；四个运行时镜像 ID 未变，`.env`、加密主密钥、租户密文/Endpoint、已启用的采集开关与巡检参数保留。
- 同版本再次应用不重建容器；损坏代码包在停止服务或迁移前拒绝，原服务继续运行。
- 已部署旧首包可只上传小脚本补丁，解压后执行 `bash apply-code.sh`。实测从没有 `.code.env` 的部署状态切换到代码发布方式成功，不重新导入镜像。
- 真实 ARM64 容器内以 `--network none`、`pip --no-index` 安装本地测试 wheel 成功；依赖变动时可随代码包携带 ARM64 wheels，宿主机无需 Python/Node/npm/make/jq。

## Docker / Compose

- 目标机仅依赖独立 `docker-compose` 命令；缺少该命令即明确报错，不尝试 `docker compose` 插件。
- 实装测试为独立 `docker-compose` 2.40.3 二进制：没有 `docker compose` 插件，也不安装宿主 Python、Node、npm、make、jq；首次部署、代码更新、状态检查均通过。
- Compose v1.29+ 的兼容文件移除 `name`、`pull_policy`、完成式迁移依赖等旧 CLI 不接受的字段，保留其他健康依赖；不使用多个 `--env-file`。四种兼容配置已通过 Compose 1.29.2 官方 JSON Schema 校验，另有模拟 CLI 测试；未声称已在每个 v1/Engine 组合上实装。
- 代码更新阶段拦截并禁止 Docker pull/load/save/build/buildx/import，更新流程仍通过。

## 验证边界

没有在用户目标 ARM64 真机执行。QEMU 环境触发 Redis ARM64 内核自检，只有临时验收覆盖文件忽略该检查；生产包保留原保护。HTTP 验收走禁止外网的内部网桥，没有把临时网络或任何自检忽略选项带入交付包。不能将本报告解释为真实 HCS 接口联调或目标机内核兼容性保证。

Python 3.12 运行时内的代码与 wheel 更新不需要传镜像；更换 Python 主版本或系统级库仍需单独调整基础环境。
