# HCS-Inspector 接续开发任务书（代码优化清单 + Claude Code 任务卡）

> 基线：**v0.4.0**（提交 `5efb196`，2026-10-23）。本文件是后续开发的**任务来源**：每完成一张任务卡，在 §3.1 总览里更新状态和提交号。
> 与 `docs/后期开发方案.md` 的关系：那份是团队路线图（B01–B28，含联调、演练、上线等人工事项）；本文件把其中**纯开发能完成**的部分，

## 0 使用方式

### 0.1 准备

```bash
unzip hcs-inspector-repo-*.zip && cd hcs-inspector   # 仓库快照含完整 .git 历史（tag v0.4.0）
make init        # Python 3.12 + Node 22
make check       # 基线：102 passed；ruff / mypy / vue-tsc / 前端构建全部通过
claude           # 在仓库根目录启动 Claude Code，自动加载 CLAUDE.md
```

仓库里已经放好的 Claude Code 配置：

| 文件 | 作用 |
| --- | --- |
| `CLAUDE.md`、`backend/CLAUDE.md`、`frontend/CLAUDE.md` | 项目说明、硬性约束、完成定义、前后端速查（自动加载） |
| `.claude/settings.json` | 权限：放行 make / pytest / ruff / mypy / alembic / npm run / git 查看与提交；`git push`、`git tag`、docker、安装依赖需确认；禁止读取 `deploy/.env`、`backend/.env`、数据 / 备份目录、证书，禁止改已发布迁移 |
| `.claude/commands/` | 自定义命令：`/task T04`、`/check`、`/new-api <描述>`、`/probe-review <文件>`、`/release 0.5.0` |

个人偏好放 `.claude/settings.local.json`（已加入 `.gitignore`）。

### 0.2 每张卡的节奏

1. `/task T01`：Claude 读卡和相关代码，先给计划（改哪些文件、是否迁移、怎么测、风险、待确认问题），**你确认后**再动手
2. 建分支 `task/T01-xxx` → 先写测试再实现 → `make check`
3. Claude 按卡片「验收」逐条给证据（命令输出、数字）→ 你看 diff → 合入 `main`
4. 每完成一个阶段（§3.1 的 Phase）发一个版本：`/release 0.4.1` → 打 tag → CI 产出镜像和离线包

不用自定义命令时，可以直接这样说：

```text
请按 docs/接续开发任务书.md 完成任务卡 T04。先读 §0、T04 卡片和它引用的 C01，再读相关代码；
先给出计划（改动文件、迁移、测试、风险、需要我确认的问题），等我确认后再改代码。
完成后运行 make check，逐条对照卡片的验收标准给出证据，并更新文档和 CHANGELOG。
```

### 0.3 通用完成定义（每张卡都要满足）

- `make check` 通过；T02 完成后，涉及数据库的改动还要 `make test-pg` 通过
- 新逻辑有测试；修缺陷先写能复现的失败用例
- 改模型 → 新迁移（修订号按合入顺序递增，可 downgrade，兼容 SQLite 与 PostgreSQL）

## 1 代码体检结论（基线 v0.4.0）

### 1.1 指标

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 规模 | 后端 `app` 13,450 行 + `mock_hcs` 1,244 + 迁移 774 + 测试 2,134；前端 `src` 9,662 行 | 中等，单人可维护 |
| 测试 | 102 个用例全过，约 23 秒；行覆盖率 **90%**（9,379 条语句，未覆盖 964） | 好；进程入口、SSE、调度偏低 |
| 静态检查 | ruff（E / F / I / B / UP）、mypy（`check_untyped_defs`）、vue-tsc 均 0 错误 | 规则偏宽 |
| 复杂度 | 14 个函数圈复杂度 > 12，最高 26（`ledger/importer.py::parse`） | 集中在导入、探测、演示数据 |
| 扩展规则试跑 | 141 条：位置参数过多 30、无用 `noqa` 21、未用参数 17、`print` 15、可变类属性 7、循环改推导式 6 …… | 多为小问题 |
| 严格类型 | 开 `disallow_untyped_defs` 后 262 处：api 168、services 62、ledger 14、notify 9、rules 6、hcs 3 | 主要是缺返回类型 |
| 重复代码 | 低：只有通知页两个弹窗、系统管理三个面板有小段重复 | 好 |
| 前端产物 | 入口 299 KB（gzip 101 KB）；ECharts 独立 chunk 547 KB（gzip 183 KB，懒加载）；CSS 374 KB（gzip 51 KB） | 可接受 |
| 前端工程 | 无 ESLint / Prettier / 单元测试 / E2E；接口类型手写；95 个路由只有 30 个声明了响应模型 | 需补 |

### 1.2 做得好的（保持）

- 分层清晰：`api → services → models`，采集器只负责“调 HCS + 标准化”；接口为同步 `def`（线程池），SSE 用 async + `asyncio.to_thread`
- 安全基础扎实：pbkdf2 20 万次、租户凭据 AES-256-GCM、登录锁定、全量写操作审计、写接口权限声明有测试兜底、对 HCS 只读
- 可靠性：Redis 分布式锁 + APScheduler `max_instances=1` / `coalesce`、通知 Outbox + `SKIP LOCKED`、部分唯一索引兜底“同一指纹只有一条活动告警”、分页参数有上限、台账释放保护
- 运维友好：JSON 日志带 `request_id`、`make status`、进程心跳与平台自身告警、数据清理、`/metrics`、生产配置自检
- 迁移测试覆盖 upgrade → 与模型一致 → downgrade → upgrade；后端镜像非 root 运行

### 1.3 一句话结论

- **正确性**：C01（跨租户同 ID 资源串数据）是唯一的 P0 级代码缺陷；C02（只在 SQLite 上测试，生产是 PostgreSQL）是 P0 级质量缺口
- **性能**：DataArts 逐个串行查状态、告警流水线 N+1、台账列表全量加载后内存分页，资源量上来后会拖慢巡检周期和页面
- **安全**：令牌无法吊销（改密码 / 退出后旧令牌仍有效）、未配置 CSP
- **工程**：覆盖率 90% 但进程入口为 0%；前端缺 lint / 单测 / 类型契约

### 2.2 详情

**C01 多租户资源身份（P0）**

- 证据：
  - `models/resource.py`：`UniqueConstraint("resource_type", "resource_id")`（全局唯一，不含租户 / 项目）
  - `services/pipeline.py::upsert_resource`：只按类型 + ID 查找；`res.tenant_id = res.tenant_id or ctx.tenant_id` —— 第二个租户的同 ID 资源会写进第一个租户的记录，状态、指标、属性互相覆盖
  - `ledger/sync.py::apply_snapshot`：“不在本项目范围内、但资源 ID 已存在的记录：直接归入本项目” —— 两个项目交替同步时，记录在租户之间来回“搬家”，变更留痕与释放判断错乱
  - `collectors/dataarts.py`：资源 ID = `工作空间/作业名`，没有工作空间时就是作业名 —— 两个租户有同名作业（如 `ods_sync`）必然冲突
  - `collectors/ecs.py`：重启次数统计查 `ResourceChange` 时只按类型 + ID 过滤
  - `ledger/importer.py::parse`：同 ID 多条时只按资源类型消歧，然后取第一条
- 影响：数据串租户 —— 告警挂错资源、负责人等运维字段被覆盖；租户范围受限的用户可能看到其他租户写入的状态 / 指标（**隔离问题**）
- 触发条件：UUID 类资源（ECS / EVS / VPC ……）跨租户基本不会重复；会重复的是**按名称标识**的资源（DataArts 作业等）、同一资源在多个项目下可见（共享 VPC / 子网），以及演练时把同一套账号录成两个租户
- 方案：项目内唯一 + 查找 / 收编 / 导入都按项目范围（T04）

**C02 只在 SQLite 上测试（P0）**

- 证据：`.gitlab-ci.yml` 的 `backend-check` 用 `sqlite:///./ci.db` 跑迁移、`alembic check`、bootstrap；`tests/conftest.py` 固定临时 SQLite
- 生产差异点：部分唯一索引 `uk_alarm_active`、`notify/dispatcher.py` 的 `with_for_update(skip_locked=True)`、JSONB、**VARCHAR 长度**（SQLite 不校验，PG 超长直接报错）、带时区时间、`ilike`、NULL 排序、Alembic batch 模式与原生 DDL 的差别
- 方案：测试可切换到 PostgreSQL + CI 增加 PG 作业 + 方言相关用例（T02）

**C03 / C19 会话安全（P1）**

- 证据：`core/security.py::create_token` 有效期 12 小时 / “7 天免登录” 7 天；`core/deps.py::load_user` 只校验用户存在、用户名一致、未停用 —— 改密码、退出登录后旧令牌在有效期内仍可用；没有 `/auth/logout`（退出只清前端）
- 令牌存 `localStorage`（`frontend/src/api/request.ts`），`deploy/nginx/snippets/security-headers.conf` 有 nosniff / X-Frame-Options / Referrer-Policy / HSTS，**没有 CSP**
- 方案：`token_version` + `jti` 黑名单 + CSP（T07）

**C04 DataArts 实时作业采集（P1）**

- 证据：`collectors/dataarts.py` 对每个作业调用 `/v1/{project_id}/jobs/{name}/status`，串行；`hcs/factory.py::DEFAULT_QPS` 每服务 5 QPS → 300 个作业约 60 秒，接近或超过采集周期；`name` 直接拼进路径，中文 / 空格 / `#` 会出错
- 所有采集器都没有并发；`hcs/ratelimit.py::TokenBucket` 已加锁，可以安全共享
- 方案：URL 编码 + 两段式 + 有界并发 + QPS 可配置 + 调用量记录（T05，合并 B06）

**C05 / C22 查询效率（P1）**

- C05 证据：`services/pipeline.py::process_observations` 每个资源一次 SELECT；每个“观测 × 规则”一次 `db.get(EvalState)` + flush + 查活动告警 —— 200 个资源 × 多条规则就是上千条 SQL
- C22 证据：`api/v1/resources.py` 台账列表 `sorted(db.scalars(q).all(), ...)` 后 `rows[(page - 1) * page_size: page * page_size]` —— 每翻一页都把全部匹配资源（含 JSON 列）读出来
- 方案：批量预取 + SQL 排序分页（T06）

**C06 / C07 运行时细节**

- C06：`core/metrics.py` 文件头已注明“只统计本进程”，而 `backend/Dockerfile` 默认 `--workers ${API_WORKERS:-2}`，经同一端口抓取时轮到不同 worker，计数不单调
- C07：`core/events.py::publish` 每次 `redis.Redis.from_url(url)`
- 方案：默认单 worker（或多进程指标）+ 复用 Redis 客户端（T08）

**C08 导出**：`core/xlsx.py` 普通 Workbook 整本在内存中生成；`api/v1/pod_events.py` 导出 `limit(50000)`，台账导出无上限 → write-only + 流式 + 统一上限（T09）

**C09–C21** 见对应任务卡，证据都已写进卡片。

### T01 测试与工具链基线

- **覆盖**：C10（工具部分）、C11、C12
- **目标**：有覆盖率报告和门槛；测试无资源泄漏、更快；Python 版本声明统一为 3.12
- **步骤**
  1. `backend/pyproject.toml` 的 `dev` 增加 `pytest-cov>=5`；在**干净的 venv** 里重新生成锁文件（`rm -rf backend/.venv && make init && make lock`），确认 `constraints.txt` 只多了 pytest-cov、coverage
  2. 覆盖率配置：`[tool.coverage.run] source = ["app"]`，`omit = ["app/services/seed*.py"]`（演示数据不计入，提交信息里记录调整前后数字）；`[tool.coverage.report] show_missing = true`、`skip_covered = true`、`fail_under = 88`
  3. Makefile 增加 `cov`（终端报告 + `backend/htmlcov/`）；`.gitignore` 增加 `.coverage`、`htmlcov/`
  4. CI `backend-check`：`pytest --cov=app --cov-report=term --cov-report=xml --junitxml=report.xml`，配置 GitLab `coverage:` 正则与 `artifacts:reports`（junit、cobertura）；CI 命令里去掉多余的 `-q`（pyproject 的 `addopts` 已有 `-q`，叠加后输出过简）
  5. 资源泄漏：`pytest -W always::ResourceWarning` 定位 13 条 “unclosed database”：`mem_db` 夹具补 `engine.dispose()`，检查测试和 `tools/status.py` 等处其他 `create_engine(...)` 是否释放
  6. 提速：慢点是会话启动写演示数据（`test_api.py::test_health` setup 5.1 秒）和 `test_bootstrap.py::test_demo_seed_after_bootstrap_without_admin`（4.9 秒），二选一：
