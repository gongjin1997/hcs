# 执行器并发与期限只读复核（2026-11-10）

范围：`services/task_execution.py`、`services/execution_runtime.py`、`workers/executions.py`。这三个文件仅阅读与隔离探针调用，未作修改；pipeline/scheduler继续由主代理整合。工作区中有主代理并行修改，以下结论对应本次读取快照，合入前需对照最新实现。

## P1：首次数据库读取不受子进程独立定时器保护

位置：`backend/app/workers/executions.py` 的 `_run_child`，读取 `db.get(TaskExecution, execution_id)` 后才根据持久deadline建立 Timer（当前约46–53行）。Supervisor也先查询数据库，再决定是否停止超时子进程。

触发：已领取任务在子进程首次获取数据库连接或读取执行记录时阻塞，且监督器因同一数据库故障也无法完成查询。此时子进程尚未建立声称独立于数据库的硬期限Timer，不能保证在任务deadline到达后退出。数据库恢复后可以回收记录，但这不能替代故障期间的进程期限保护。

隔离验证：Mock SessionLocal的首次get延迟后抛连接异常，记录Timer构造调用；观察到整个阻塞期间Timer从未构造。没有真实数据库故障注入或生产访问。

建议主代理：claim成功时把有限deadline/启动保护预算随启动参数传给子进程，在首次DB操作之前启动独立watchdog；数据库读回的deadline只能收紧。父进程Child也保存可独立检查的单调时钟期限，不把所有kill判断放在成功数据库读取之后。状态写回仍应保留owner-token/lease栅栏。

## P2：缺失执行记录会永久占用已退出子进程的槽位

位置：`backend/app/workers/executions.py` 的 `Supervisor.tick`，`SELECT ... FOR UPDATE SKIP LOCKED` 返回None时直接continue（当前约159–163行），尚未检查process是否退出，也未调用_release。

触发：执行记录不存在，例如被删除或随InspectionRun级联删除。该返回与暂时被提交事务锁住的返回混在一起；即使子进程已经退出，children中的对象仍永久保留。并发数为1时，此后tick不会领取新任务；并发数为N时损失一个槽位，直至监督器重启。

隔离验证：数据库scalar返回None，Child.process.is_alive返回False且exitcode=124，并发设为1；调用真实Supervisor.tick后，已退出child仍在children，process.close和claim_next均未调用。

建议主代理：区分不存在和暂时锁定；已确认退出的子进程必须释放本地资源/槽位，数据库记录回收可交给后续reap。暂时锁定时也应保留独立进程退出/期限检查，避免无限continue。对仍在提交的活动子进程继续遵守现有提交栅栏。

## 已检查但未认定为缺陷的部分

- claim使用数据库锁与QUEUED条件更新；不能仅凭SQLite缺少FOR UPDATE就认定一定双领。
- runtime在提交前核对status、owner_token、lease、cancel和deadline，并将终态与运行记录放在同一提交中；ExecutionStopped继承BaseException，普通采集局部异常不能吞掉它。
- 读取期间主代理已补充SAVEPOINT跳过、队列过期按QUEUED限定等处理，未将旧快照中的相关问题作为当前缺陷报告。
